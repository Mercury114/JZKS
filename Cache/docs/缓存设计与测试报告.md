# 缓存设计与测试报告

## 1. 目标、基线与来源

设计范围为I/D缓存、直接映射与多路LRU、写回写分配、Cache管理指令、I侧流水化，以及CPU、主存、外设的公共接入。

基线为小组 `D-cache` 分支 `3487cdd`。原 `D-cache/` 为同伴的独立四路D-Cache，原 `Exp9_源码_v文件/rtl/mycpu_top.v` 实为多周期CPU。
为满足分工文档的五级流水集成要求，新增 `rtl/cpu/` 复用个人课设提交 `6de28bfaf3fa0b7d55f7011616e244f2b30d98a1` 的五级核心并做握手/CACOP适配，原目录不覆盖。
新集成版D-Cache继承同伴实现，修改点与个人贡献分别见 [我的完成说明](我的完成说明.md)。

## 2. 系统结构

```text
     IF / ID / EXE / MEM / WB       cache_cpu
          |           |   \ CACOP
          |           |    \ 管理路由与序列化
     I-Cache      D-Cache
        |      回填 | 写回       I/D uncached旁路
        +-----------+--------------+
                   轮转仲裁器
           四字整行 / 单字事务适配
                       |
                逐字主存握手端口
                       |
             一拍SRAM桥（课程SoC）
                 /        |       \
             指令RAM   数据RAM   原confreg
```

`cache_system` 是通用外部主存入口；`cache_soc_lite_top` 是课程内存/外设连接入口。
仲裁器每次只向主存保留一个未完成字请求，整行拥有者在四个字全部完成前不切换。

## 3. 缓存组织与LRU

默认每个缓存256组、2路、16B/行，容量为 `256×2×16=8192B`。
地址划分为tag `[31:12]`、index `[11:4]`、offset `[3:0]`；word为 `[3:2]`，byte lane为 `[1:0]`。
每路保存valid、tag、4个32位数据字和LRU rank，D侧另有dirty。

- `WAY_NUM=1`：直接映射，每组唯一路。
- `WAY_NUM=2/4`：所有路并行比较，优先填最低编号无效路。
- rank=0表示最近使用，rank最大者最久未使用；命中和回填均更新顺序。
- I侧无效化压紧有效排名；D侧为所有路维持唯一rank，包括无效路。两种表示均实现同一条“有效行按最近使用顺序替换”的规则。
- D替换有效脏行时，先把原tag、原组号对应的完整16B写回，再回填新行。

`INDEX_WIDTH` 参数改变组数，tag宽度随之变化；行大小固定16B，支持1/2/4路，不支持任意路数或任意行长。

## 4. 统一请求和完成协议

### 4.1 CPU到缓存

CPU通过 `*_sram_en` 表示请求有效。有效请求在 `valid && addr_ok` 的上升沿被接受，地址、写数据、字节使能在此之前保持不变。
接受后CPU撤销请求，缓存使用锁存副本；`data_ok` 表示实际完成，load读取返回值，store只检查完成。
CPU可在接受后改变当前输出，不能因此改变已经排队的事务。

IF为一笔未完成请求保存PC，完成响应另有缓冲。跳转和WB异常重定向可取消尚未接受或已缓冲指令；
已接受的旧请求不能从主存撤回，因此设置丢弃标记，等旧响应排空再发新请求。

数据操作在EXE等待完成，返回值随指令保存后进入MEM，MEM只负责字节/半字选择和扩展。
load在EXE仍标记结果未就绪，ID不能错误前递地址；MEM有真实数据后才能前递。
store发出前等待更老MEM/WB排空，异常和中断不会让被取消的年轻store修改缓存或外设。
完成标记及“被取消的未决事务”分别跟踪，避免旧响应错认到下一条指令。

### 4.2 缓存到仲裁器

- `rd_req && rd_rdy`：一条16B读请求被接受。
- `ret_valid`：一个32位字到达；允许空拍，只有有效字推进计数，第四字带 `ret_last`。
- `wr_req`：D缓存提出16B写回，地址/128位数据保持稳定。
- `wr_rdy`：仲裁器已收到四个字的写完成响应，整个写回完成。

I/D模块均支持读请求被接受的同拍返回首字。正常回填必须恰好四字、按顺序返回，不支持错误响应、乱序或中止半行。

### 4.3 仲裁器到主存

主存端口为 `mem_valid/write/wstrb/addr/wdata`、`mem_ready`、`mem_rvalid/rdata`。
`valid && ready` 接受一个字；`rvalid` 完成这个字，包括写完成。支持同拍完成，也支持任意正延迟。
没有接受就不得返回响应；若复位取消事务，CPU、缓存、仲裁器和主存侧必须共同复位清空所有未完成响应。

## 5. D-Cache写策略

写命中按四位 `wstrb` 合并目标字，并置dirty；未选中字节不改变，零strobe不把clean行变脏。
写未命中采用write-allocate：选victim、必要时写回、读整行、按字节合并本次写入，最后完成原store。

状态顺序为：

```text
IDLE -> RESP                                    命中
IDLE -> [WB_REQ] -> REFILL_REQ -> REFILL_WAIT
     -> REFILL_APPLY -> RESP                    未命中
IDLE -> [CTRL_WB] -> CTRL_DONE                   管理
```

所有等待状态只使用已锁存的请求；外部valid或payload变化不会导致重复store。
管理支持无效化、只写回、写回后无效化三种内部操作；CPU的CACOP使用初始化及写回后无效化教学子集。

## 6. 外设、内存映射和一致性

外设判定沿用原桥：`(address & 0x1fff0000) == 0x1faf0000`。
外设单字旁路，不分配缓存；保留完整地址低位和原始写数据/字节使能，不擅自增加地址别名。
原confreg是稀疏、精确地址译码，任意非零we会更新整个寄存器；它并非普通RAM式byte merge，本实现不更改这一已有语义。

课程SoC代码区 `1c00_0000~1c0f_ffff` 对应1MiB指令RAM，支持D侧写回以验证自修改代码；
其它非外设地址对应原256KiB数据RAM镜像。`BOARD_ADDR_MAP=1` 在缓存前把数据地址高位归一化，
因此 `0x100`、`0x40100`、`0x80000100` 使用同一缓存物理地址；CACOP地址也走相同归一化。
通用 `cache_system` 默认不启用该截位规则，实际外部主存可实现完整地址空间。

I/D之间没有自动一致性监听。修改可执行代码时使用 **D写回无效化→I命中无效化→重新取指**；
实际测试先执行旧函数，再通过D写入新指令，经两条CACOP后执行新值。
本课程实现不包含MMU、DMW/MAT、DMA、多核一致性或AXI。

## 7. CACOP教学子集

编码 `[31:22]=0000011000`，code在原rd字段，地址为 `R[rj] + SignExtend(si12)`。

| code | 目标 | 操作 |
|---|---|---|
| 00 | I | 指定way/index初始化：清tag、置无效 |
| 01 | D | 指定way/index初始化：清tag、置无效、清dirty，不写回 |
| 08 | I | 指定way/index无效化 |
| 09 | D | 指定way/index脏行写回后无效化 |
| 10 | I | tag命中则无效化，未命中无操作 |
| 11 | D | tag命中则脏行写回后无效化，未命中无操作 |

索引模式way来自地址最低位：1路忽略，2路取bit0，4路取bit[1:0]，index仍取缓存组号位。
CACOP不要求字对齐，不写通用寄存器；CPU在最高权限执行，非法code/权限分别走INE/IPE。
管理指令在ID等待老指令提交，EXE等待cache管理完成，WB冲刷至自身PC+4。

语义参考：[龙芯LoongArch参考手册CACOP节](https://loongson.github.io/LoongArch-Documentation/LoongArch-Vol1-EN.html#_cacop)。
这里采用课程用的清tag/无效化初始化，不实现新版规范的任意 `CSR.CTAG` StoreTag，也不实现TLB转换和其它缓存级别；不能声称完整LoongArch系统缓存规范均已实现。

## 8. I-Cache流水化

设E为请求接受沿：

| 时点 | 行为 |
|---|---|
| E | 锁存tag/index/word |
| E至E+1 | 并行比较各路tag并查询数据；若miss立即关闭下一请求的addr_ok |
| E+1命中 | 更新rdata/data_ok，同沿可接受下一请求 |
| 连续命中 | 之后每周期一接受、一响应 |
| miss | 阻塞新请求，回填四字后响应；最后一个请求字可从返回数据直接旁路 |

独立测试对连续32拍接收和连续32拍返回均做断言，不仅看最终值。
CPU IF目前只允许一笔未完成请求，未充分利用I-Cache本体的一拍吞吐；D-Cache也是阻塞式，未做D命中流水。
该设计满足本次I侧流水化拓展，不等同于非阻塞Cache、多MSHR或整机1IPC。

## 10. 公平的性能对比

所有模式使用同一个五级CPU、同一程序、同一逐字主存模型，每字固定 `LATENCY=8`、关闭随机空拍。
有缓存模式保持**I/D各512B等容量**：直接映射32组×1路、两路16组×2路、四路8组×4路，均16B行。
这与默认I/D各8KiB配置不同，避免把容量增加误说成关联度收益。
终点为同一条标记指令写回；最终脏数据通过程序中的CACOP实际写回，比较包含这些周期。

| 原创短程序 | 无缓存 | 直接映射 | 两路 | 四路 |
|---|---:|---:|---:|---:|
| 热点循环 | 13,121 | 3,196 | 3,196 | 3,196 |
| 同组双行冲突循环 | 13,121 | 14,499 | 3,285 | 3,285 |
| 冷启动＋SMC＋异常 | 1,297 | 1,399 | 1,399 | 1,399 |

热点循环缓存约4.11倍周期加速；冲突程序两路约4.00倍快于无缓存，约4.41倍快于直接映射。
直接映射冲突程序比无缓存更慢，冷启动管理程序也没有收益，不能宣称缓存总是加速。

| 程序/配置 | I命中/请求 | D命中/请求 | 主存字读/字写 |
|---|---:|---:|---:|
| 热点/直接映射 | 715/722 | 255/256 | 28/5 |
| 冲突/直接映射 | 715/722 | 128/256 | 536/513 |
| 冲突/两路 | 715/722 | 254/256 | 32/9 |
| 冲突/四路 | 715/722 | 254/256 | 32/9 |

I统计包含被接受的预取/后来取消的请求，不是提交指令数；无缓存不计算“命中率”。
CPU、cache和总线计数口径分别保留，不能互换。

另在**低延迟课程SRAM桥**运行原ex9：无缓存690,083周期、直接映射825,491、两路819,922、四路815,786。
这些模式默认组数相同、容量不同，只作为原教师功能回归中的周期观察，不作为等容量关联度实验。
这个低延迟场景缓存整体更慢，说明当前阻塞式接入和整行回填的开销可能超过命中收益。
上述是相同时钟假设下的周期比较，不是综合后频率或真实板卡运行时间。
